# Doc Templates and Authoring Guide

> Templates and conventions for ADRs, RFCs, and Memos. Every internal doc should start from one of the templates in this directory and follow the rules below. The binding architectural source of truth is `docs-internal/adr/`; this guide makes sure new and edited docs land in the right shape.

## Pick the right doc type

| You want to… | Use | Filename | Hub |
|---|---|---|---|
| Record a binding architectural rule the project must follow | **ADR** | `adr-NNN-<slug>.md` | `adr-002-readme.md` |
| Propose, explore, or specify an architecture or feature | **RFC** | `rfc-NNN-<slug>.md` | `rfc-002-readme.md` |
| Capture operational notes, investigations, diagrams, post-mortems, demoted decisions, how-tos | **Memo** | `memo-NNN-<slug>.md` | `memo-031-docs-internal-hub.md` |

If the doc is **not stating a rule the project commits to**, it's a memo — even if it touches architecture. ADRs are short and rule-shaped; RFCs are long and proposal-shaped; memos are everything else.

When demoting an ADR (because it never was a binding rule, or because it pinned implementation details that don't belong in an ADR), see the **Demotion checklist** below.

## Universal rules

These apply to all three doc types.

1. **Filename: lowercase kebab-case** — `adr-018-document-identification-system.md`. Never uppercase, never spaces, never `ADR-` / `RFC-` / `MEMO-` prefixes in filenames. (References in prose may still use uppercase IDs like `ADR-018`.)
2. **Numbering is monotonic and unique within the type.** Pick the next free number. The doc index hubs list the latest IDs.
3. **Every doc starts with frontmatter** (see schema per type). `id`, `title`, `status`, `type`, `created`, `author`, `project_id` are required everywhere. Every doc gets a unique `doc_uuid` (generate with `uuidgen | tr '[:upper:]' '[:lower:]'`).
4. **First content line after frontmatter is `# <ID>: <Title>`.** Then a 2–4 line blockquote stating the doc's essence. A reader who only reads the blockquote should know whether to keep reading.
5. **No emojis** unless the doc is itself about emojis or a user explicitly asked for them.
6. **No AI co-author footers, no "generated by …" markers, no Claude/Copilot signatures.**
7. **Cross-references** use relative paths: `[ADR-009](adr-009-provider-abstraction-architecture.md)`. The `related:` frontmatter list is just IDs (`ADR-009`, `RFC-021`, `MEMO-062`).
8. **Don't pin specific package versions in ADRs.** Version pinning belongs in `package.json` / `go.mod`. If you find yourself writing `^1.2.3` in an ADR, you've written a memo.
9. **Don't bundle two decisions in one ADR.** Split it.
10. **Don't paste large code listings.** Link to source paths (`pkg/docid/uuid.go`) or to an RFC that holds the long form.
11. **Don't include implementation status checklists, "Future Work" sections, measured-results tables, or session/incident logs in an ADR or RFC.** Those go in a memo.
12. **When you change an ADR, RFC, or memo, also update the relevant hub** (`adr-002-readme.md`, `rfc-002-readme.md`, `memo-031-docs-internal-hub.md`) in the same change.
13. **Run `./scripts/docs-validate.sh` before committing.** It must end green.

## Frontmatter — controlled vocabularies

Pick from these. If your doc legitimately needs a new value, add it here in the same change.

### `status` (per type)

| Type | Allowed values |
|---|---|
| ADR | `Draft`, `Proposed`, `Accepted`, `Implemented`, `Deprecated`, `Superseded` |
| RFC | `Draft`, `Proposed`, `Accepted`, `Implemented`, `Withdrawn`, `Superseded` |
| Memo | `Draft`, `Final`, `Reference`, `Archived` |

No parenthetical suffixes (`Implemented (Phase 1)` is invalid — use `Implemented` and explain phasing in the body).

### `type`

Exactly one of: `ADR`, `RFC`, `Memo`. (Not `MEMO`, not `memo`, not `Guide` — the legacy memo `type` values are inconsistent and being normalized.)

### `decision_type` (ADR only — required)

One of:

- `Architectural Pattern`
- `Authentication`
- `Backend Architecture`
- `Build System`
- `Configuration`
- `Data Model`
- `Frontend Architecture`
- `Infrastructure`
- `Testing Strategy`

If your ADR doesn't fit any of these, the ADR is probably a memo. Talk it through before adding a new category.

### `subtype` (optional, RFC and Memo)

Free-form short label, Title Case (`Architecture`, `Authentication`, `Frontend Compatibility Note`, `Investigation`, `Diagrams`, `Playbook`). Avoid synonyms — reuse an existing subtype if one fits.

### `supersedes`

When a doc supersedes another (e.g. memo demoted from an ADR, ADR replaced by a newer ADR), set `supersedes: ADR-NNN`. The superseding doc's opening blockquote must explain *why* it superseded the prior doc.

### `related`

List of IDs (`ADR-009`, `RFC-021`, `MEMO-062`). Order: ADRs first, then RFCs, then memos, each numerically ascending.

## Demotion checklist

When converting an ADR into a memo (because it isn't a binding architectural rule):

1. `git mv docs-internal/adr/adr-NNN-<slug>.md docs-internal/memo/memo-MMM-<new-slug>.md`.
2. Rewrite the frontmatter for memo conventions: change `id`, `title`, drop `decision_type`, set `supersedes: ADR-NNN`, set `type: Memo`, set a memo-appropriate `status` (usually `Final` or `Reference`).
3. Rewrite the opening blockquote to explain the demotion in one sentence.
4. Strip rule-shaped language ("MUST", "is required") and reframe as historical/operational notes.
5. Update `adr-002-readme.md`:
   - Decrement the ADR total and the affected category count.
   - Remove the row from the index table.
   - Remove or update any cross-cutting principles row that referenced the ADR.
   - Add a row to the **Demoted to Memos** table.
6. Update `memo-031-docs-internal-hub.md` to add the memo to the appropriate category.
7. Grep for inbound references: `rg "ADR-NNN" docs-internal/ AGENTS.md` — fix every hit (`related:` lists, prose, hub tables).
8. Run `./scripts/docs-validate.sh`.
9. Commit as a single focused change with an imperative-mood message: `docs(adr): demote ADR-NNN to MEMO-MMM`.

## Migration checklist (ADR narrative → RFC)

When an ADR has grown narrative, benchmarks, migration phases, or worked use cases:

1. Create `rfc-NNN-<slug>.md` with `supersedes: ADR-NNN (narrative content)`.
2. Move the narrative into the RFC; keep the ADR tight (rule + context + consequences + alternatives).
3. ADR adds a "See RFC-NNN for…" line in Context, and adds the RFC to its `related:` list.
4. Update both hubs (`adr-002-readme.md` "Narrative Migrated to RFCs" table, `rfc-002-readme.md`).
5. Validate, commit.

## Known docs-process gaps (track here as discovered)

- `./scripts/docs-validate.sh` currently scans 0 files due to a `docs-project.yaml` path resolution issue; validation is effectively a no-op until that is fixed.
- Legacy memos use inconsistent `type:` values (`MEMO`, `memo`, `Memo`, `Guide`, `Analysis`, `Playbook`, `milestone`). New docs must use `Memo`; a sweep to normalize legacy memos is open work.
- Some legacy IDs are referenced but missing on disk: `RFC-007`, `RFC-020`, `RFC 034`, `ADR-007`, `ADR-016`, `MEMO-001`, `MEMO 075`. See `adr-002-readme.md` "Known-Missing Legacy References".
- Filename casing: docuchango expects lowercase `adr-NNN-…` etc.; some legacy files retain uppercase prefixes and trigger validation warnings.
